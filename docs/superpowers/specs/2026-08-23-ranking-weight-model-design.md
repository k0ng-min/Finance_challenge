# 가중치 점수 기반 보험사 순위 설계 (2026-08-23)

## 왜 바꾸나

지금 순위는 두 단계다. `insurer_ranking.py`가 약관 근거 네 축으로 상대 단계를 매기고,
`insurer_ranking_score_gemini.py`가 그 결과에 등급별 보장금액을 얹어 Gemini에게 점수를
매기게 한 뒤 재정렬한다.

여기에 세 가지 문제가 있다.

1. **"내 여행 준비"에서 고른 것들이 순위에 거의 안 들어간다.** 목적지·활동·걱정되는
   사고유형·동행·기존보험을 다 물어봐 놓고, 순위를 가르는 건 약관 네 축과 Gemini의
   판단뿐이다. 네 축은 "그 보험사의 약관이 어떻게 쓰여 있는가"에서 나오는 값이라 사용자가
   무엇을 골랐든 변하지 않는다.
2. **순위가 재현되지 않는다.** 같은 입력에 같은 순서가 나오는지가 모델에 달려 있다.
   "왜 이 보험사가 1위인가"를 수식으로 되짚을 수 없다.
3. **가격이 아예 빠져 있다.** 현재 프롬프트는 "보험료는 자료에 없습니다"라고 못 박는데,
   실제로는 `insurer_premium`에 나이·성별·등급별 실제 조회값이 있다.

## 무엇을 만드나

(보험사 × 등급)마다 다섯 축의 점수를 계산하고, 사용자가 고른 것으로 축의 가중치를
정한 뒤 합산해 순위를 낸다. 최종 점수는 **가중치 점수 8 : Gemini 점수 2**로 섞는다.

### 축

| 축 | 내용 | 자료 | 등급 따라 변함 |
|---|---|---|---|
| A. 사고유형별 보장금액 | 21개 보장항목을 사고유형에 매핑해 금액을 점수화 | `insurer_comparison_metric` | 예 |
| B. 약관 근거 | 기존 네 축(보장적합·조건명확·청구간편·제한적음) | `insurer_ranking.py` | 아니오 |
| C. 가격 | 사용자의 나이·성별·등급·여행일수로 조회한 실제 보험료 | `insurer_premium` | 예 |
| D. 기존보험 보완도 | 이미 든 보험과 겹치면 감점, 비는 곳을 메우면 가점 | `external_policy`, `overlap_rule` | 예 |
| E. 활동·목적지 대응 | 활동 관련 특약·면책, 목적지 여행경보 | `clause`, `travel_alert` | 아니오 |

### A축 정규화 — 등급별 순위가 달라지는 원리

항목별로 **6개사 × 3등급 = 18개 값을 한 묶음으로** 놓고 0~1로 정규화한다. 등급 안에서만
정규화하지 않는 것이 요점이다.

- 등급을 올려도 금액이 그대로인 항목(예: DB 해외상해의료비 5000/5000/5000)은 세 등급에서
  같은 점수를 받는다.
- 등급에 따라 크게 뛰는 항목(예: 카카오페이 3000/5000/10000)은 실속에서 낮고 고급에서
  높은 점수를 받는다.

그래서 **같은 가중치를 써도 등급마다 순서가 달라진다.** 차이를 억지로 만들어내는 게 아니라,
등급 간 금액 차이가 실제로 있는 만큼만 순서에 반영된다. 차이가 없으면 순서도 같다.

### 21개 항목 → 사고유형 매핑

| 항목 | 사고유형 |
|---|---|
| 상해사망보험금 / 상해후유장해보험금 / 국내 상해의료비(급여) / 해외 상해의료비 / 상해입원일당 | INJ |
| 질병사망·고도후유장해 / 해외 질병의료비 / 국내 질병의료비(급여) / 식중독 보상 / 특정전염병 보상금 | ILL |
| 국내 3대 비급여의료비 / 국내 비급여 MRI·MRA | INJ·ILL 절반씩 |
| 휴대품손해(분실제외) / 자택도난손해 / 여권분실 재발급비용 | PROP |
| 배상책임 | LIA |
| 수하물·항공편 지연 / 출국항공기지연(지수형) / 항공기납치위로금 | TRV |
| 여행중단 추가비용 | CHG |
| 중대사고 구조송환비용 | EMG |

SPC(전쟁·천재지변 등)에 해당하는 보장금액 항목은 없다. 없는 걸 억지로 만들지 않고
A축에서 SPC는 0으로 둔다 — 대신 B축(약관 근거)에는 SPC 조항이 잡힌다.

### 여행 준비 선택 → 가중치

| 선택 | 반영 |
|---|---|
| 걱정되는 사고유형(coverage_priority) | 그 유형 A축 항목 가중치 ×3 |
| 활동(activities) | 활동→사고유형 매핑으로 가산, E축에도 반영 |
| 목적지 여행경보 단계 | EMG·ILL 가산 |
| 여행 기간(start~end) | 길수록 ILL·CHG 가산. C축 보험료는 일수로 환산 |
| 동행 유형(companion_type) | 가족 → LIA 가산, 반려동물 → SPC 가산 |
| 렌터카(rental_car) | LIA 가산 |
| 나이 | 높을수록 ILL·EMG 가산 |
| 기존보험 | 겹치는 유형 감산(D축) |
| 비교 기준(tier_code) | 축 A~E 사이의 비중 자체를 조정 |

### C축 — 가격 자료가 없는 보험사

`insurer_premium`에는 지금 삼성·현대·KB·카카오페이 네 곳만 있다. 메리츠·DB는 자료가
없다. **없는 자료를 0점으로 세지 않는다** — 그 두 곳은 C축을 빼고 남은 축의 가중치를
다시 100%로 맞춰 계산하고, 화면에 "가격 자료 없음"이라고 밝힌다. 나중에 두 곳의 보험료가
들어오면 아무것도 고치지 않아도 C축에 자동으로 포함된다.

## R은 어디에 쓰나

R은 **가중치와 정규화 계수를 만드는 분석 도구**로 쓴다. 서버가 돌 때 R이 필요하지는 않다.

```
backend/data/app.db
   │  analysis/export_ranking_inputs.py   (KB → CSV)
   ▼
analysis/data/coverage_amounts.csv, premiums.csv
   │  analysis/ranking_weights.R          (분석 → 계수 산출)
   ▼
backend/app/data/ranking_weights.json     (저장소에 커밋)
   │  backend/app/services/ranking_score.py
   ▼
순위
```

R이 하는 일:
- 21개 항목의 분포와 **등급 간 실제 격차**를 계산한다. 등급을 올려도 안 변하는 항목과
  크게 뛰는 항목을 갈라내, 등급 차이를 실제로 만드는 항목에 더 큰 비중을 준다.
- 항목별 정규화 계수(min·max)를 산출한다.
- 사고유형별 기본 가중치와 비교 기준별 축 비중을 표로 만든다.
- 산출물을 `ranking_weights.json` 하나로 쓴다.

R을 런타임에서 빼는 이유는 배포 때문이다. Render 백엔드는 파이썬 런타임이라 R을 실행하려면
Docker로 갈아타야 하고, 무료 플랜에서 빌드 시간과 배포 위험이 함께 커진다. 계수를 파일로
떨어뜨려 커밋하면 R의 분석 결과를 그대로 쓰면서 배포는 지금 그대로 둘 수 있다.

## Gemini 혼합

```
최종 점수 = 가중치 점수 × 0.8 + Gemini 점수 × 0.2
```

둘 다 0~100으로 맞춘 뒤 섞는다. Gemini가 실패하면 가중치 점수만으로 순위를 낸다 —
순위가 LLM 가용성에 묶이지 않는다. Gemini에게는 계산된 축 점수와 약관 근거를 함께 넘겨,
수식이 놓친 맥락(예: 특정 활동이 면책으로 걸려 있음)만 보태게 한다.

## 화면

순위 카드에 "왜 이 순서인지"를 축별 기여도로 보여준다. 지금 있는 네 축 표시를 다섯 축으로
늘리고, 각 축이 이번 순위에 몇 점 기여했는지와 그 근거(금액·조항·보험료)를 같이 붙인다.

## 검증

- 축별 점수 계산은 단위 테스트로 고정한다(정규화, 결측 처리, 가중치 적용).
- **같은 입력에 같은 순서**가 나오는지 테스트한다.
- **등급을 바꾸면 점수가 실제로 달라지는지**, 그리고 **금액 차이가 없는 항목만 있는 경우
  순서가 그대로인지** 둘 다 테스트한다.
- 가격 자료가 없는 보험사가 그 이유로 불리해지지 않는지 테스트한다.

## 안 하는 것

- 객관적 확률·전문가 평점을 만들지 않는다. 축 점수는 6개사 사이의 상대 비교값이다.
- 근거가 없는 항목을 추정으로 채우지 않는다. 없으면 그 축을 빼고 재정규화한다.
- 서버 실행 경로에 R을 넣지 않는다.
