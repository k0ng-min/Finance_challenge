## 1. 「해외 서류 챙기기」(/onsite)에서 에러 배너 — 원인: 서버에 없는 여행 ID

배포 API에 직접 찔러 본 결과는 이랬다.

| 요청 | 결과 |
|---|---|
| `GET /onsite?country=일본` | 200 |
| `GET /onsite` (나라 없음) | 200 |
| `GET /trips/9/onsite` (실제 있는 여행) | 200 |
| `GET /trips/999999/onsite` (없는 여행) | **404** |

API는 멀쩡했다. 문제는 프론트가 **localStorage에 남은 여행 ID를 검증 없이 그대로 믿는** 것이었다.
`AppContext`는 사고 ID(`incidentId`)는 서버 목록과 대조해 고쳐 잡으면서 여행 ID는 그러지 않았다.
그래서 그 여행이 이미 없으면 — 게스트 토큰이 사라져 계정이 새로 만들어졌거나, 게스트가 새 여행을
등록하며 앞 기록이 정리됐거나, **Render 무료 플랜이라 재배포 때마다 사용자 데이터가 날아가거나** —
나라를 고르기도 전에 그 ID로 요청이 나가 404가 났다.

고친 곳:

- `frontend/src/context/AppContext.tsx` — 사고 ID와 똑같이 여행 ID도 `listTrips`로 대조한다.
  없으면 지우고, 다른 여행이 있으면 가장 최근 것으로 맞춘다.
- `frontend/src/pages/Onsite.tsx` — 나라를 **직접 골라서** 보낸 요청이 실패했을 때만 빨간 배너를
  띄운다. 등록한 여행 기준으로 자동으로 나간 요청이 실패한 것뿐이면 사용자는 아무것도 누른 적이
  없으므로, "나라를 고르면…" 안내로 되돌린다.

확인: 헤드리스 브라우저로 `travel_ai_trip_id=999999`를 심고 `/onsite`를 열었더니 배너 없이
안내 문구가 뜨고, localStorage의 값도 `null`로 정리됐다.

## 2. 「청구 전 점검」(/checklist)에서 "실수 방지 점검하러 가기"가 안 넘어감 — 원인: 같은 화면으로 되돌아옴

## 3. 「사고가 발생했어요」 추가 질문의 "장해" — 오타가 아니었다

실제 문구는 `backend/app/seed_questions.py`의
"후유장해 진단을 받으셨다면 장해 정도(%)가 어떻게 되나요?"였다. **장해는 약관 정식 용어다** —
약관에 장해분류표·장해지급률로 나오고(`seed_db_2026_c.py`), 표준담보 이름도 `상해사망·후유장해`,
서류도 `장해진단서`다. 진단서에 그 이름으로 적혀 있어야 사용자가 찾을 수 있으므로 "장애"로 바꾸면
오히려 못 찾는다.

그래서 용어는 두고 뜻을 괄호로 풀었다:

> 후유장해(치료를 마친 뒤에도 남는 신체 기능의 영구 손상) 진단을 받으셨다면, 진단서에 적힌
> 장해지급률이 몇 %인가요?

같이 고친 것 두 가지:

- `seed_questions.py`의 `run()`이 여태 `applies_to_l1/l2`만 갱신해서, 질문 문장을 고쳐도 이미
  시드된 DB(배포 서버 포함)에는 옛 문장이 그대로 남았다. 이제 문장과 가중치도 맞춘다.
- `incident_questions_gemini.py`의 프롬프트에 "약관 용어를 쓰면 괄호로 짧게 풀어 주라"는 규칙을
  넣었다 — 이 화면 질문은 대부분 Gemini가 그때그때 만들기 때문에, 시드만 고쳐서는 반만 고친 것이다.

## 4. 청구 검토 결과에 해당 담보의 가입금액 표시 — 원인: 약관에 금액이 없었다

`coverage_amount` 필드는 원래 있었는데 값이 거의 안 찼다. 이유가 둘이었다.

1. 금액을 약관 조항(`Coverage.limit_amount`)에서만 찾는데, 그게 적힌 담보는 **170개 중 27개**뿐이다.
2. 그 27개마저 상당수가 `"보험증권 기재 금액"`, `"보상한도액(보험증권 기재)"` 같은 **숫자 없는 문구**다.
   약관은 금액을 증권으로 미루기 때문이다.

실제 숫자는 다른 데 있었다 — 보험사 공시에서 받아온 등급별 가입금액표(`InsurerComparisonMetric`,
7개 보험사 × 등급마다 21개 항목이 빠짐없이 채워져 있다). 표준담보코드로 그 표를 찾도록 이었다.

- `backend/app/services/coverage_amounts.py` (신규) — `std_code → metric_label` 매핑과 조회.
  등급을 모르면(`UserPolicy.plan_name`이 비었으면) 지어내지 않고 비운다. 숫자가 아닌 표기
  ("-", "가입", "미제공")는 금액으로 내보내지 않는다. 비교표에 대응 항목이 없는 담보
  (반려동물 돌봄, 골프용품손해, 상해 고도후유장해 특약 등)는 **일부러 매핑에 넣지 않았다** —
  비슷해 보이는 항목에 억지로 잇는 순간 다른 담보의 금액을 이 담보 금액인 것처럼 보여주게 된다.
- `analysis_finding.plan_amount` 컬럼 신설(마이그레이션은 `app/schema_migrations.py` — 아래 7번 참고).
  약관 한도와 성격이 달라 같은 칸에 섞지 않는다 — 약관에만 있는 "1개당 20만원" 같은 조건이
  사라지면 안 되고, 반대로 약관 한도만 보여주면 정작 숫자가 없다.
- `FindingCard.tsx` — **가입금액**(등급 기준)과 **약관 한도**를 두 줄로 나눠 보여준다.

확인: 로컬에서 DB손보 실속형으로 사고를 접수해 API 응답을 직접 봤다.

| 담보 | 약관 한도 | 가입금액(신규) |
|---|---|---|
| 상해사망·후유장해 | (없음) | 상해사망보험금 10,000만원 · 상해후유장해보험금 10,000만원 (실속형 기준) |
| 해외 상해의료비 (급여) | (없음) | 5,000만원 (실속형 기준) |
| 중대사고 구조송환비용 | 보험증권 기재 금액 | 3,000만원 (실속형 기준) |

DB손보 실속형 기준으로 그 사고에 걸리는 담보 168건 중 128건이 금액을 갖게 됐다.

## 5. 「약관 형광펜」이 화면을 그리기 전에 AI 호출 62번을 순서대로 기다렸다

`ClauseHighlight.tsx`는 조항마다 Gemini를 2번씩(관련도 + 쉬운말) 부른 뒤에야 화면을 그렸다.
코드 주석에는 **"조항 개수가 적어(보통 3~6개)"** 라고 적혀 있었는데, 실제로 상해 사고 한 건을
접수해 보니 **조항이 31개**였다. 62번을 순차로 기다린다는 뜻이고, 그동안 사용자에게는
"이 사고와 관련된 부분을 찾고 있어요"만 떠 있다(측정: 3분이 지나도 안 끝났다).

조항 원문은 이미 응답에 들어 있는데 기다릴 이유가 없었다. 원문부터 바로 보여주고 형광펜
표시는 준비되는 대로 그 자리에 채우도록 바꿨다. **조항이 보이기까지 1.5초.**
순차 조회 자체는 그대로 뒀다 — 한꺼번에 쏘면 무료 티어 분당 한도를 넘어 조용히 실패한다.

같이 드러난 것 세 가지도 고쳤다.

- **취소 처리가 없었다.** 사고를 바꾸면 앞 사고의 조회가 계속 돌아 새 목록 위에 덧칠됐다.
  (원래는 화면이 다 끝난 뒤에만 그려져서 눈에 안 띄었을 뿐, 조건은 똑같이 성립했다.)
- **"쉬운 말로 보기"가 거짓말을 했다.** 아직 안 만들어졌을 뿐인데 "지금은 쉬운말 설명을
  만들 수 없어요"라고 떴다. "준비하고 있어요"와 "만들 수 없어요"를 구분한다.
- **"(관련도 순)" 표기.** 정렬은 전부 준비된 뒤 한 번만, 그것도 사용자가 아직 첫 조항에서
  움직이지 않았을 때만 한다(읽는 중에 재배열하면 보던 조항이 눈앞에서 바뀐다).
  그래서 실제로 정렬됐을 때만 그 표기를 붙인다.

## 6. `/mistakes`로 들어오면 엉뚱한 탭이 열렸다

옛 경로 `/mistakes`는 `/checklist`로 리다이렉트되는데, 그러면 항상 첫 탭(서류 체크)이 열렸다.
실수 방지를 보러 온 사람에게 서류 체크를 여는 셈이다. `?tab=mistakes`를 붙여 원래 보려던
탭이 열리게 했다.

## 7. 테스트가 커밋 대상 DB를 고치고 있었다 (그리고 그 덕에 통과하고 있었다)

`plan_amount` 컬럼을 추가하자 E2E 3건이 `no such column`으로 깨졌다. 파고들어 보니 구조 문제였다.

- 스키마 맞추기(`_add_missing_columns`)가 `main.py` **모듈 최상위**에 있었다. 앱을 띄울 때는
  돌지만, 커밋된 `data/app.db`를 사본으로 떠서 쓰는 `conftest.kb_session`에서는 안 돈다.
- 그런데도 여태 통과했던 이유가 더 문제였다 — 테스트가 `app.main`을 import하는 순간 그
  마이그레이션이 **운영 DB 파일에** 돌아 컬럼을 붙여 놓았기 때문이다. 즉 통과의 근거가
  "테스트가 원본 파일을 고쳤다"였다. `reset_guest_data.py`가 배포 전마다 지우던
  게스트 흔적의 출처도 같은 경로다.

고친 내용:

- `backend/app/schema_migrations.py` (신규) — `apply(engine)` 하나로 떼어냈다. `main.py`와
  `conftest.kb_session`이 각자의 DB에 같은 코드를 부른다.
- `backend/app/database.py` — `DATABASE_URL` 환경변수로 DB 경로를 바꿀 수 있게 했다.
  경로가 상수로 박혀 있는 동안에는 "다른 DB로 띄운다"는 방법 자체가 없었다.
- `backend/tests/conftest.py` — app.* 을 import하기 전에 `DATABASE_URL`을 임시 파일로 돌린다.
  이제 테스트를 돌려도 `data/app.db`의 해시가 변하지 않는다(확인함).
- `backend/tests/test_clause_search.py` — 전역 engine으로 운영 DB를 직접 열던 유일한 테스트라
  다른 테스트와 같이 `kb_session` 사본을 쓰도록 바꿨다.

QA용으로는 사본을 쓴다(`.gitignore`에 `backend/data/qa*.db` 추가):

    cd backend
    cp data/app.db data/qa.db
    DATABASE_URL="sqlite:///./data/qa.db" python -m uvicorn app.main:app --port 8010
