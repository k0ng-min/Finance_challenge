## 데이터: 7개사 약관을 어떻게 정제해서 쓰는가

> 2026-08-25에 **신한EZ손해보험 「신한 SOL 처음해외여행보험」**(2026.06.06 시행판, 236쪽)을
> 7번째 보험사로 추가했습니다. 조항 117건·담보 29건을 적재했고 원문 대조를 100% 통과합니다.
> 실제 보험료(244행)도 이후 직접 조회해 채웠으므로 지금은 7개사 모두 가격 축이 들어갑니다.
> 다만 실속케어·안심케어 2등급만 판매해 고급 등급 비교에서는 제외되고, 그 사유를 화면에 밝힙니다.


`data/raw_pdfs/`의 실제 약관 PDF(보험사당 162~326쪽, 2026-08-18 재구축분)를 다음 단계로 구조화해 SQLite(`backend/data/app.db`)에 담습니다.

1. **원문 추출** — pdfplumber로 페이지 단위 텍스트 추출. 표 레이아웃 때문에 열 라벨이 문장 중간에 끼어드는 경우만 제거하고, 나머지는 원문을 한 글자도 바꾸지 않습니다.
2. **조항 단위 분해(`Clause`)** — 조(제N조) 단위로 잘라 `clause_type`(보장정의/면책/제한/조건/서류/공통)을 붙입니다.
3. **표준 담보 매핑(`Coverage` ↔ `CoverageStd`)** — 보험사마다 다른 특약명(예: "여행중 배상책임 특별약관" vs "배상책임보장 특별약관")을 표준 담보 코드(`LIABILITY` 등)로 묶어, 같은 성격의 담보를 보험사 간에 비교할 수 있게 합니다.
4. **사고유형 매핑(`ClauseIncidentMap`)** — 이 프로젝트의 핵심 축. "무슨 사고가 났나"(사고유형)와 "무슨 담보로 받나"(coverage)를 분리해서, 조항 하나하나를 사고유형(L1 8개 고정 + L2 31개, 아래 참고)에 `직접`/`조건부`/`면책`으로 매핑합니다. 담보가 늘어나도 사고 판단 로직 자체는 늘어나지 않는 구조입니다.
5. **수치 조건 구조화(`ClauseTerm`)** — 조항 원문 안의 지급한도·자기부담금·지연기준시간·보상일수한도 등 숫자를 뽑아 별도로 저장합니다. 값의 근거가 된 원문 조각(`raw_text`)은 반드시 조항 원문의 부분 문자열이어야 하며, 이를 벗어나면 절대 저장하지 않습니다(`raw_text_is_grounded()` 검증).
6. **필요서류 매핑(`CoverageDocMap`)** — 담보별 청구 필요서류를 표준 서류 코드(`RequiredDocStd`, 14종)에 연결합니다.

**현재 데이터 규모**는 맨 위 「지금 담고 있는 것」에 있습니다 — 그 숫자는 손으로 옮겨 적지 않고 `backend/scripts/generate_docs.py`가 DB에서 세어 씁니다. 여기에 하나만 덧붙이면, 청구서류가 성립하는 담보 163건은 **전부** 필요서류가 연결돼 있습니다(100%). 원본 재구성 스크립트는 `backend/app/seed_*.py`에 남아 있습니다.

이 숫자를 여기에 적어두는 것만으로는 계속 낡습니다(실제로 보험사가 7개로 늘어난 뒤 위 숫자가 한동안 어긋나 있었습니다). 그래서 앱 안의 「보험 형광펜」 화면 아래쪽에 **근거 검증 현황** 구획을 두고, 지금 이 서버의 DB에서 그 자리에서 세어 보여줍니다 (`GET /insurers/kb-stats`). 통과율이 100%가 아닌 항목도 그대로 내보입니다 — 못 채운 자리를 가리면 채운 자리의 숫자까지 믿을 수 없게 되기 때문입니다.

이 정제 파이프라인을 직접 수행한 방법과 원칙은 `backend/PDF_EXTRACTION_PLAYBOOK.md`, `backend/CLAUSE_TERM_DOC_PLAYBOOK.md`에 정리돼 있습니다 — 특히 "원문에 없는 내용은 절대 지어내지 않되, 원문에 실제 있는 내용은 빠뜨리지 않는다"는 두 원칙을 항상 같이 지킵니다.

### 사고유형(incident_type) 체계

8개 대분류(L1, 고정)와 그 아래 소분류(L2)로 구성됩니다.

- **INJ 상해**: 상해사망·후유장해 / 해외상해치료 / 귀국후 국내치료
- **ILL 질병**: 질병사망·고도후유장해 / 해외·국내 질병치료 / 감염병·격리
- **PROP 휴대품·재물**: 도난 / 파손 / 분실 / 현금·유가증권 / 여권분실
- **LIA 배상책임**: 대인 / 대물 / 임차물·호텔객실
- **TRV 운송**: 항공지연·결항 / 수하물지연·분실 / 항공기납치
- **CHG 여행변경**: 여행취소 / 여행중단·조기귀국
- **EMG 긴급지원**: 수색구조 / 의료이송 / 유해송환 / 가족방문비용
- **SPC 특수·기타**: 전쟁·테러(면책) / 천재지변 / 반려동물돌봄 / 그 외 미분류

8개 L1은 절대 늘리지 않고, 새로운 사고유형은 L2로만 확장합니다. 기존 L2 어디에도 맞지 않는 조항·사고가 나오면 조용히 버리지 않고 `needs_review=True`로 새 L2를 만들어 사람이 나중에 검수하도록 표시합니다(현재 "식중독보상금(입원)", "자택 도난손해(가재)" 2건이 이렇게 생성돼 있습니다).

## 작동 방식 (런타임 흐름)

1. **사고 자유서술 입력** — 사용자가 사고 상황을 문장으로 입력합니다.
2. **1단계 분류(L1)** — Gemini가 자유서술만으로 8개 대분류 중 하나를 즉시 판정합니다(`incident_classify_gemini.classify_l1`).
3. **2단계 확인 질문(L2)** — 판정된 L1에 태그된 질문(`question_bank.applies_to_l1`)만 골라 던집니다. 예: INJ면 진단명/입원여부, TRV면 지연시간처럼 대분류마다 다른 질문 세트가 미리 정의돼 있습니다.
4. **2단계 분류(L2)** — 답변이 쌓일 때마다 Gemini가 그 L1 안의 L2 후보 중 하나로 재분류합니다. 이미 충분히 확신 있게 분류됐으면(신뢰도 임계치 이상) 매번 다시 묻지 않고 재사용해 API 호출을 아낍니다.
5. **담보 매칭** — 확정된 사고유형(type_id)에 `직접`/`조건부`/`면책`으로 매핑된 조항을 가진, 사용자가 등록한 실제 담보만 추려냅니다. 사고 상황의 수식자(활동 등, 예: "스쿠버다이빙")가 면책 조항 원문에 실제로 언급돼 있으면 "직접" 조항이 같이 걸려 있어도 면책을 우선 표시합니다(과도하게 낙관적인 안내 방지).
6. **결과 생성** — 관련 조항(형광펜 근거), 수치 조건(ClauseTerm), 필요서류(CoverageDocMap)를 담보별로 묶어 보여줍니다. 각 카드 설명에는 Gemini가 이번 사고 내용에 맞춰 조항·서류를 풀어 설명한 문장이 자동으로 덧붙습니다(`explain_clause_plain`, `explain_docs_for_incident`) — 실패해도 예외를 삼키고 기본 설명으로 대체되므로 흐름이 끊기지 않습니다.
7. **보험 형광펜** — 사고 상황과 직접 관련된 조항 구간만 노란색으로 표시(`/clauses/{id}/relevance`). 인용은 항상 조항 원문의 부분 문자열인지 대조 검증을 거칩니다.
8. **누락·모순 검증** — LLM을 쓰지 않는 결정적 규칙(`services/validation.py`)으로 보험기간 불일치, 정보 누락, 입력값 모순(예: 수술은 받았는데 입원은 아니오) 등을 별도로 확인합니다.

담보를 찾지 못하면 "청구검토후보"라고 억지로 말하지 않고 "확인불가"로 정직하게 답합니다(근거 없는 결과 금지).

## 기존보험 연결 — 중복·공백 진단

여행자보험은 이미 들고 있는 실손·상해·일상생활배상책임과 담보가 겹치는 구간이 있습니다. 사용자가 기존보험을 등록하면 **이번 여행자보험과 겹치는 담보·비는 담보를 약관 원문 근거와 함께** 보여줍니다.

### 이 기능의 축을 바꾼 이유

처음 구상은 "같은 보험사의 기존계약이 있으면 받는 혜택"이었습니다. 그런데 당시 확보돼 있던 6개사 약관 363개 조항을 전문 검색한 결과 **관련 조항이 한 건도 없었습니다.**

| 키워드 | 건수 | 키워드 | 건수 |
|---|---|---|---|
| 할인 | 0 | 기존계약 | 0 |
| 우대 | 0 | 다수계약 | 0 |
| 기가입 | 0 | 가입경력 | 0 |

데이터 누락이 아니라 구조적 사실입니다. 보험료 할인율은 약관이 아니라 보험료산출방법서·사업방법서(금감원 제출용, 비공개)와 각 사 마케팅 정책에 있습니다. 약관은 "보상하는 손해 / 면책 / 지급절차"만 다룹니다.

그래서 근거가 실재하는 **중복보장 진단**으로 축을 옮겼습니다. 혜택·할인 안내는 약관이 아닌 별도 출처가 필요하므로 이 범위에서 분리했습니다(아래 "남은 작업" 참고).

### 판정을 코드가 아니라 데이터로 둔다

`overlap_rule` 테이블에 **행마다 근거 조항(`clause_id`)과 그 조항 원문 속 핵심 문구(`anchor_phrase`)를 물려서** 시드합니다. 근거 없는 판정이 구조적으로 불가능해집니다.

시드 스크립트(`seed_overlap_rules.py`)는 `relation`이 `UNKNOWN`이 아닌 규칙에서 근거 조항을 못 찾거나 `anchor_phrase`가 실제 조항 원문에 없으면 **예외를 던지고 롤백합니다.** `clause_id`를 상수로 박지 않고 (보험사명, 조항 제목, 표준담보, 조항 종류)로 조회하므로 약관을 재시드해도 어긋나지 않습니다.

현재 시드된 판정 7건:

| 기존보험 | 여행자보험 담보 | 구간 | 판정 | 근거 |
|---|---|---|---|---|
| 상해보험 | 상해사망·후유장해 | 전체 | 겹치지만 **각각 다 받음**(정액) | 삼성 제3조 "약정한 보험금을 지급합니다" |
| 실손 | 해외발생 질병의료비 | 국내 의료기관 | **일부 겹침** | 삼성 \<붙임3\> "실제 본인이 부담한 의료비" |
| (모든 기존보험) | 여권분실 재발급비용 | 전체 | **비례보상** | 삼성 제1조 "…비율에 따라 보험금을 지급합니다" |
| (모든 기존보험) | 항공기납치 | 전체 | **택일 보상** | 현대 제3조 "하나의 계약에서만 보상" |
| 실손 | 해외 상해·질병의료비 | 해외 의료기관 | **확인불가** | — |
| 일상생활배상책임 | 배상책임 | 전체 | **확인불가** | — |

확인불가 3건은 처음엔 근거를 붙여 단정했지만, 검토 과정에서 **인용한 조항이 그 주장을 뒷받침하지 않는다**는 것이 드러나 내렸습니다. 예를 들어 "기존 실손은 국내 의료기관만 보상한다"는 판정의 근거로 달았던 조항은 *삼성화재 여행자보험* 제3조였는데, 이 조항은 *이 여행자보험이* 해외 치료비를 보상한다는 내용일 뿐 기존 실손의 보장 범위는 말하지 않습니다. 실손 표준약관은 이 프로젝트가 보유하지 않으므로 **판정을 내리는 대신 확인불가로 남겼습니다.**

인용문은 `anchor_phrase`를 포함하는 구간을 잘라내므로, 근거 문장이 조항 뒷부분(예: 여권분실 조항의 445번째 글자)에 있어도 화면에 잘려 나가지 않습니다. 자를 때 말줄임표를 붙이지 않으므로 인용문은 **항상 원문의 연속 부분 문자열**입니다.

### 기존보험을 어떻게 가져오는가

수집 방식을 `ExternalPolicyProvider` 인터페이스 뒤에 숨기고 세 구현체를 둡니다. 저장·진단·화면은 수집 방식을 구분하지 않습니다.

| Provider | 로그인 | 상태 |
|---|---|---|
| `manual` | 불필요 | 사용자가 종류를 직접 선택 (게스트도 가능) — **배포 기본값** |
| `mock` | 필요 | 연동 UX 시연용 고정 샘플 (기본 꺼짐) |
| `codef` | 필요 | **스키마·필드매핑만 작성, 호출 미구현** |

`EXTERNAL_POLICY_PROVIDERS` 환경변수로 활성 방식을 정하고, `GET /users/{id}/external-policies/providers`가 그 목록을 알려줍니다. 기본값은 `manual` 하나입니다 — mock을 켜 둔 채로 배포하면 화면에 뜬 고정 예시(삼성화재 실손 등)가 실제 조회 결과처럼 보이기 때문에 기본값에서 뺐습니다. 시연·테스트 환경에서만 `EXTERNAL_POLICY_PROVIDERS="manual,mock"`으로 켜고, 이때 API는 그 방식이 시연용임을 `is_demo`/`notice`로 함께 내려줍니다.

**CODEF를 실제로 연결하지 않은 이유:** 담보별 중복 판정에 필요한 보장 상세를 주는 것은 신용정보원 '내보험다보여'뿐인데(생명보험협회 '내보험찾아줌'은 계약 상태만 제공), 이 서비스는 회원가입에 **주민등록번호**가 필요합니다. 개인정보보호법 제24조의2는 주민등록번호를 법령에 구체적 근거가 있을 때만 처리하도록 하며 정보주체 동의로 갈음할 수 없습니다. 본 서비스에는 그 근거가 없으므로 `CodefProvider.fetch()`는 `NotImplementedError`를 던집니다. 운영 주체가 법적 요건을 갖춘 뒤 이 구현체만 채우면 나머지 코드는 그대로 동작합니다.

### 실손은 가입시기만 물어봅니다

실손의료보험은 2009년 표준화 이후 보험사별 보장내용이 동일합니다(보험다모아: *"4세대 실손의료보험은 보험회사별 보장내용은 모두 표준화되어있지만, 보험료는 사업비 구조, 적용위험률 등에 따라 다를 수 있습니다"*). 그래서 가입 년월만 받아 세대를 판정합니다 — 사용자가 자기 가입금액을 몰라도 됩니다.

| 세대 | 가입시기 |
|---|---|
| 1세대 | ~2009-09 |
| 2세대 | 2009-10 ~ 2017-03 |
| 3세대 | 2017-04 ~ 2021-06 |
| 4세대 | 2021-07 ~ |

가입시기를 모르면 추측하지 않고 세대를 비워 둡니다. 실손 외 종류(상해·일상생활배상책임·운전자)는 표준약관이 없어 회사·상품마다 담보가 다르므로 종류만 저장합니다 — 중복 *판정* 자체는 종류만으로 되므로 진단은 정상 동작합니다.

### 화면

| 위치 | 내용 |
|---|---|
| 내 보험 보관함(`/policies`) | 기존보험 등록·삭제, 진단 결과 (로그인 계정) |
| 여행 준비(`/trip`) | 마지막 확인 단계 앞에 기존보험 선택 |
| 사고 접수(`/incident`) | 최종 단계 앞에 기존보험 선택, 결과 화면에 진단 표시 |

기존보험 선택은 **건너뛰어도 여행 등록·사고 접수가 정상 완료되는 선택 항목**입니다. 저장은 본 흐름을 막지 않도록 백그라운드로 흘려보냅니다.

### API

```
GET    /users/{user_id}/external-policies/providers        사용 가능한 수집 방식
GET    /users/{user_id}/external-policies                  목록
POST   /users/{user_id}/external-policies/link             등록(모든 provider 공통 진입점)
DELETE /users/{user_id}/external-policies/{id}             삭제
GET    /users/{user_id}/coverage-overlap?trip_id=&user_policy_id=   진단
```

진단은 **조회 시점에 매번 계산하고 저장하지 않습니다.** 약관 DB가 갱신되면 결과도 자동으로 따라오고, 저장하면 약관이 바뀌었을 때 낡은 결과가 남기 때문입니다.

### 알려진 한계

- **여행 준비 화면에서는 게스트가 진단 결과를 볼 수 없습니다.** 진단이 뜨는 조건인 "내 보험 등록"이 비로그인은 로그인 화면으로 보내기 때문입니다(기존 기능의 전제). 사고 접수 화면은 게스트도 정상 동작합니다.
- 확인불가 3건은 실손 표준약관을 확보해야 판정할 수 있습니다.
- `anchor_phrase`가 200자를 넘으면 인용문에서 잘릴 수 있습니다(현재 등록된 문구는 10~20자).

## 보험사 순위 — 순서는 수식이 정하고, 모델은 문장만 씁니다

"어느 보험사가 나은가"는 이 서비스가 내리는 판단 중 가장 무거운 것입니다. 그래서 순서를
LLM에게 맡기지 않습니다. 최종 순서는 `services/ranking_score.py`의 계산만으로 끝나고,
Gemini(`insurer_ranking_explain_gemini.py`)는 **이미 확정된** 순위·총점·축 기여도를 입력으로
받아 "왜 이 보험사가 위인가"를 문장으로 풀어 쓸 뿐입니다. 예전에는 모델이 매긴 점수를
결정적 점수와 섞어 정렬했는데, 그러면 같은 입력에 같은 순서가 나온다는 보장이 없습니다.

계산은 두 겹입니다.

**1층 — 약관 근거 4축**(`services/insurer_ranking.py`): `coverage_fit`(걱정한 사고를 챙겨줘요),
`condition_clarity`(조건이 숫자로 또렷해요), `claim_simplicity`(청구가 간단해요),
`restrictions`(막히는 조건이 적어요)를 KB에서 계산해 1~5 상대 단계로 바꿉니다. 보험사의 전체
면책 조항 **개수**는 쓰지 않습니다 — 같은 내용을 한 조항에 모아 쓰느냐 여러 조항으로 나누느냐는
약관 작성 방식의 차이일 뿐인데, 그게 점수 차이로 읽히기 때문입니다. 근거를 확보하지 못한 축은
0점이 아니라 `UNKNOWN`("나쁘다"가 아니라 "모른다")으로 내보냅니다.

**2층 — 5축 종합 점수**(`services/ranking_score.py`): 가입등급(0=실속/1=표준/2=고급)을 함께
받으면 (보험사 × 등급)마다 `amount`(등급별 보장금액)·`clause`(1층 결과)·`price`(나이·성별·등급에
맞는 실제 보험료)·`overlap`(기존보험 위에 새로 얹어주는 정도)·`activity`(이번 여행의 위험 대응)를
0~1로 내고, 여행 준비에서 고른 것으로 정한 비중을 곱해 0~100 총점을 만듭니다. 축별 점수·비중·
기여도가 API 응답에 그대로 실려 나가므로 "왜 1위인가"를 응답 안에서 끝까지 되짚을 수 있습니다.

세 가지를 지킵니다.

- **자료가 없는 축은 0점이 아니라 제외.** 비중에서 빼고 남은 축을 다시 100%로 맞춥니다.
  없는 자료를 0점으로 세면 "자료가 없다"가 "나쁘다"로 읽히고, 보험료 자료를 아직 못 구했다는
  이유만으로 순위가 밀립니다. 내려간 축도 응답에서 지우지 않고 `available=false`와 사유를 남깁니다.
- **겹침 축도 약관 근거로만.** 중복 진단 화면과 **같은 엔진**(`coverage_overlap.diagnose`)을
  부르고 대상 담보만 바꿉니다. 두 화면이 서로 다른 말을 하는 일이 구조적으로 생기지 않습니다.
- **보험료는 값의 출처를 가립니다.** `DIRECT_QUOTE`와 환산 근거가 명시된 `DERIVED`만 쓰고,
  보간한 `IMPUTED`는 축에서 뺍니다. 여행일수로 새 견적을 만들지도 않습니다 — 보험료가 기간에
  선형 비례한다는 근거가 없기 때문입니다.

정규화 구간과 항목→사고유형 매핑, 축 비중은 손으로 고른 값이 아니라 `analysis/ranking_weights.R`이
실제 KB 값을 분석해 `backend/app/data/ranking_weights.json`으로 떨어뜨린 것입니다(서버 실행에는
R이 필요 없습니다). 방법론 전문은 [`docs/ranking_methodology.md`](docs/ranking_methodology.md).

### 우리가 고른 숫자가 순위를 흔드는가

축 비중이나 "스키를 타면 상해 무게를 0.5 올린다" 같은 계수는 약관에서 나온 값이 아니라 우리가
정한 정책 계수입니다. 그 숫자가 조금 달랐다면 1위가 바뀌었을지를 재봐야, 우리가 보여주는 것이
근거인지 우리가 고른 숫자인지 알 수 있습니다. `analysis/ranking_sensitivity.py`가 대표 시나리오
8개(결과를 보기 전에 정했고 하나도 빼지 않았습니다)에 대해 계수를 하나씩 ±10·20% 흔드는 OAT와
전부 한꺼번에 흔드는 몬테카를로를 합쳐 2,048회 돌립니다. 결과는 Top-1 유지율 계수 OAT 99.3% /
축 비중 OAT 95.6% / 몬테카를로 91.0%입니다. 전문과 시나리오별 표는
[`docs/ranking_sensitivity.md`](docs/ranking_sensitivity.md).

### 1-1. 보험료·담보 가입금액표 데이터 (선택)

2026-08-19부터 보험다모아 비교공시 대신, 각 사 다이렉트 사이트에서 **직접 조회한 실제
등급(플랜)별 가격**을 씁니다. 저장소엔 이미 적재된 상태로 포함돼 있어 그대로 쓰면 됩니다.
원본 엑셀은 `backend/data/source_files/`에 있고, 새로 조회한 값으로 갱신하고 싶으면 같은
경로에 같은 형식(시트명·열 순서)으로 엑셀을 덮어쓴 뒤 아래를 실행하세요 — 보험사별로
테이블을 통째로 갈아끼웁니다.

```bash
python -m app.seed_premiums_actual   # insurer_premium: 나이·성별·등급별 실제 보험료
python -m app.seed_plan_coverage     # insurer_plan_coverage: 등급별 담보 가입금액표
```

가격 데이터는 7개사 전부 확보돼 있습니다(insurer_premium 2,794행). 다만 전부 같은 급의
값은 아닙니다 — 화면에서 그대로 받아온 값(DIRECT_QUOTE) 2,186행, 기간 환산처럼 변환 근거가
명시된 값(DERIVED) 486행, 산술 보간한 추정값(IMPUTED) 122행입니다. IMPUTED는 `value_origin`
기준으로 보험사 순위의 가격축에서 제외하고, 화면에도 "산술 보간한 추정 보험료라 추천 점수에서
제외했어요"라고 사유를 밝힙니다. 시트가 없는 보험사는 조용히 건너뛰므로, 새로 조회한 값을 같은
형식의 시트로 엑셀에 추가하고 스크립트를 다시 돌리기만 하면 코드 변경 없이 채워집니다.
담보 가입금액표도 7개사 전부 확보돼 있습니다(6개사는 `seed_plan_coverage`, 신한EZ손보는 다이렉트 화면 캡처 근거로 `seed_shinhan_2026_f`).

옛 `crawl_premiums.py`/`seed_premiums.py`(보험다모아 표준조건 크롤링)는 코드만 남아 있고
더 이상 쓰지 않습니다 — 보험사가 실제로 파는 여러 등급의 가격을 보여주지 못했기 때문입니다.

여행경보도 같은 방식입니다. `backend/data/travel_alerts.json`에 수집된 상태로 포함돼 있고,
경보가 바뀌었을 때만 다시 받으면 됩니다. 갱신하려면 공공데이터포털에서 「외교부_국가·지역별
여행경보」를 활용신청해(무료·자동승인) 받은 **일반 인증키(Decoding)** 를 `backend/.env`의
`DATA_GO_KR_SERVICE_KEY`에 넣습니다. Encoding 키를 넣으면 이중 인코딩으로 인증에 실패합니다.

```bash
python -m app.crawl_travel_alerts   # data/travel_alerts.json 갱신(출처·수집일 포함)
python -m app.seed_travel_alerts    # travel_alert 테이블에 통째로 갈아끼움
```

시드가 통째로 갈아끼우는 이유는 경보가 해제되기도 하기 때문입니다 — 남겨두면 이미 풀린
경보가 계속 뜹니다.

## 배포

저장소 루트의 `render.yaml`로 [Render](https://render.com) 무료 플랜에 백엔드(FastAPI, Web Service)와
프론트엔드(정적 사이트)를 한 번에 배포합니다.

1. Render 대시보드 → **New +** → **Blueprint** → 이 GitHub 저장소 선택 → `render.yaml`을 자동으로 읽어
   `travel-insurance-api`(백엔드)와 `travel-insurance-web`(프론트엔드) 두 서비스를 생성합니다.
2. 두 서비스 모두 처음 배포가 끝나면 서로의 실제 배포 주소를 몰라 초기 화면에서 멈춥니다 — 각 서비스의
   **Environment** 탭에서 아래 값을 상대 서비스의 실제 주소로 채우고 재배포해야 합니다.
   - `travel-insurance-api`의 `FRONTEND_BASE_URL` ← `travel-insurance-web`의 실제 주소
   - `travel-insurance-web`의 `VITE_API_BASE` ← `travel-insurance-api`의 실제 주소
   - 서비스 이름이 이미 다른 사용자가 쓰고 있으면 Render가 자동으로 `-xxxx` 접미사를 붙인 주소를
     배정합니다 — 반드시 각 서비스 페이지 상단에 뜨는 실제 링크를 확인해서 넣어야 합니다.
3. (선택) `travel-insurance-api`의 Environment에 `GEMINI_API_KEY`, `KAKAO_REST_API_KEY`,
   `KAKAO_CLIENT_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`을 채우면 Gemini 기반 사고분류·
   설명과 카카오/구글 로그인이 켜집니다. 비워두면 그 기능만 자동으로 꺼진 채(규칙기반 분류, 게스트
   모드) 나머지는 정상 동작합니다.
4. 카카오·구글 로그인을 켰다면, 각 개발자 콘솔(Kakao Developers / Google Cloud Console)의 OAuth
   클라이언트에도 배포된 프론트엔드 주소 기준 리디렉션 URI를 추가로 등록해야 합니다
   (`https://<배포주소>/auth/kakao/callback`, `https://<배포주소>/auth/google/callback`) — 로컬 개발용
   `localhost` URI는 지우지 않고 그대로 둔 채 추가하면 로컬/배포 둘 다 계속 동작합니다.

무료 플랜 특성상 15분간 요청이 없으면 백엔드가 잠들어(cold start) 다음 요청이 30~60초 정도 걸릴 수
있고, SQLite가 영구 디스크가 아니라 배포 후 사이트에서 실제로 쌓인 사용자 데이터는 재배포·재시작 시
초기화될 수 있습니다(약관 원문 KB는 저장소에 커밋돼 있어 항상 그대로 복원됩니다). GitHub 저장소에
푸시하면 Render Auto-Deploy가 `main` 브랜치 변경을 감지해 자동으로 다시 빌드·배포합니다.

`backend/data/app.db`를 커밋할 때는 개발 중 쌓인 게스트 계정·여행·사고 기록이 약관 KB와 같은
파일에 섞여 diff에 그대로 드러납니다. 커밋 전에 아래로 사용자 데이터만 지우세요(약관 KB는
건드리지 않습니다):

```bash
cd backend
python -m app.reset_guest_data            # 삭제될 행 수만 미리 확인
python -m app.reset_guest_data --confirm  # 실제 삭제
```

### 이전 판 약관으로 빈칸 메우기

2026-08-18에 약관 원본을 새 PDF로 갈아끼우며 KB를 전면 재구축했습니다(89beae8). 전체로는
사고유형 매핑이 352 → 527건으로 늘었지만, 새 PDF에 실리지 않은 특약 때문에 **통째로 비어버린
자리**가 생겼습니다 — 현대해상·카카오페이의 휴대품(PROP)과 긴급지원(EMG)이 각각 0건이 되어,
현대해상으로 "휴대폰을 분실했어요"를 접수하면 관련 약관이 하나도 나오지 않았습니다.

그래서 이전 판 약관에서 **그 빈칸에만** 실제 조항 원문을 들여옵니다. 새 PDF에서 나온 조항이
하나라도 있는 자리는 건드리지 않습니다(항상 새 판이 우선). 들여온 조항에는 어느 판에서 왔는지
`clause.source_edition`에 남습니다.

```bash
cd backend
git show 89beae8^:backend/data/app.db > /tmp/kb_prev.db
python -m app.merge_archived_kb /tmp/kb_prev.db            # 무엇이 들어올지만 확인
python -m app.merge_archived_kb /tmp/kb_prev.db --confirm  # 실제 반영
python -m app.kb_manifest --confirm                        # 매니페스트를 DB에 다시 맞춤
```

KB를 고치면 `data/dataset_manifest.json`(커밋된 app.db가 무엇을 담고 있어야 하는지의 기록)과
어긋나 `scripts/validate_kb.py` 검사가 걸립니다. 이건 KB가 아무도 모르게 바뀌는 걸 잡는
장치이므로, 일부러 고쳤을 때는 위 `app.kb_manifest`로 개수와 지문만 다시 맞춥니다 — 출처
URL·PDF 해시·검증 상태처럼 사람이 원본을 확인해 적은 값은 자동으로 덮어쓰지 않습니다.

## 약관 원문

`data/raw_pdfs/`, `data/processed/`는 저장소에 포함하지 않습니다. 보험사 공식 발행 약관 PDF 원문을 재배포하지 않기 위함입니다(`docs/compliance/source_register.md`에 각사 출처·SHA-256을 기록해 두었습니다). 2026-08-18 재구축분은 공개 URL이 없는 발행 파일이라 자동 재다운로드는 불가능하다 — 조항 원문 발췌 자체는 `backend/app/seed_*_2026_*.py`와 `backend/data/app.db`에 이미 포함돼 있으므로, PDF 없이도 서버 실행과 조회는 됩니다.

## 구현 현황

- 가입 전 맞춤 추천(`POST /trips`) — 7개사 담보·면책조항 비교, 위험활동 감지
- 내 보험 보관함(`/users/{id}/policies`) — 보험사명·담보명 KB 자동 매칭
- **사고유형(L1/L2) 기반 청구 검토** + 단계별 확인 질문(`/incidents`, `/incidents/{id}/answers`) — 예전 키워드 휴리스틱 방식은 폐기됨
- 서류 체크 + 누락·모순 검증(`/incidents/{id}/checklist`, `/evidence`)
- 보험 형광펜 — 사고 상황과 직접 관련된 조항 구간만 노란색으로 표시, 검색 지원
- 조항 수치 조건(ClauseTerm) 별도 표시 — 지급한도·자기부담금 등을 배지로 분리 노출
- 활동 기반 면책 우선 판단 — 사고 상황의 수식자(예: 스쿠버다이빙)가 면책 조항과 실제로 일치하면 과도하게 낙관적인 안내를 하지 않음
- 사고 내용과 조항·필요서류를 연결한 Gemini 상황별 설명 자동 표시
- **서류 사진 확인**(`청구 전 점검 > 서류 체크`) — 해외에서 받은 서류는 당사자도 맞는 건지 알기
  어렵습니다. 사진을 올리면 번역해서 무슨 내용인지 알려주고, 요건이 실제로 담겨 있는지 대조합니다.
  결과는 **「약관이 요구하는 것」(조항 원문 인용)** 과 **「일반적으로 확인하는 것」(약관 근거 아님을
  명시)** 두 칸으로 나눠 보여줍니다 — 약관 요건은 `doc_requirement`에 근거 조항을 물려 시드하며
  (예: 제7조 ②항 *"사고증명서는 …국외의 의료관련법에서 정한 의료기관에서 발급한 것이어야 합니다"*),
  금액·진료일자처럼 약관에 없는 항목은 근거가 없으므로 상태를 바꾸지 않습니다.
  사진이 흐리거나 잘려 **판독 불가**면 "미보유"로 단정하지 않고 상태를 그대로 둔 채 다시 찍어달라고
  안내합니다. 파일 선택기를 열기 전에 **"이 사진이 Google Gemini API로 전송된다"는 고지를 먼저
  띄우고, 확인하지 않으면 어떤 경로로도 파일을 고를 수 없게** 막습니다 — 서버에 저장하지 않는 것과
  외부에 보내지 않는 것은 다른 이야기인데 예전 화면은 앞의 것만 말하고 있었습니다.
  사진은 물론 번역문도 저장하지 않고(진단서는 민감정보), 남기는 것은 체크리스트 상태와
  "약관 요건 N개 중 M개 확인" 수준의 요약뿐입니다. 사진 없이 직접 상태를 고르는 기존 방식도 그대로
  쓸 수 있으며, Gemini 키가 없으면 이 기능만 정직하게 막습니다(규칙기반 폴백이 불가능한 기능이라
  흉내내지 않습니다).
- 모든 결과는 실제 약관 조항 근거가 없으면 자동으로 "확인불가" 처리
- 인증/보안 — 카카오·구글 로그인, 회원가입 동의, 로그인 계정 간 데이터 접근 차단(IDOR 방지), 요청 빈도 제한, 보안 HTTP 헤더, CORS 제한
- **결정적 5축 순위 + 가입등급별 비교** — 순서는 `ranking_score.py`의 수식만으로 정해지고
  Gemini는 확정된 순위의 이유 문장만 씁니다. 실속·표준·고급 등급을 바꾸면 실제로 금액이 뛰는
  항목만 차이를 만들어 순서가 달라집니다. 축별 점수·비중·기여도를 응답에 그대로 실어 "왜 1위인가"를
  되짚을 수 있게 했고, 계수를 흔들어 순위가 얼마나 버티는지도 재 뒀습니다(위 전용 절 참고)
- **비교함** — 보험료 비교 화면에서 마음에 둔 보험사를 담아 두면 계정에 저장돼 나중에 다시
  찾을 수 있습니다(`GET/PUT /users/{id}/premium-watchlist`). 게스트는 서버에 저장하지 않으므로
  로그인 계정만 씁니다
- **첫 진입 둘러보기** — 무엇을 하는 서비스인지 글로 설명하는 대신, 손끝을 따라가는 다섯 장짜리
  화면으로 먼저 보여줍니다
- **금융권 수준 로그인·세션 보호** — 유휴 세션 만료, 연속 실패 5회 시 10분 자동 잠금(영구 잠금은
  두지 않습니다 — 잠금을 풀어 줄 상담 창구가 없어서 공격자가 남의 계정을 막는 수단이 됩니다),
  계정 존재 여부가 응답으로 새지 않게 막기, 그리고 표에 남기는 보안 감사 로그. 감사 로그에는
  비밀번호·세션 토큰·사고 내용을 남기지 않고 접속 주소도 비밀키를 섞은 HMAC 앞자리만 남깁니다 —
  감사 로그가 유출되면 그 자체가 2차 사고이기 때문입니다
- **사고유형 기반 보험사 비교** — 여행 준비 단계에서 고른 "걱정되는 사고유형"이 보험사 순위(지급한도가
  실제 숫자로 확인되는 담보는 가점)에 반영되고, 보험사 상세화면에서 그 사고유형 버튼을 누르면 그
  보험사의 실제 약관 조항을 바로 나열(자동추천 탭 대신)
- **사고-여행 연동** — 서류체크·실수방지점검·보험형광펜 화면에 연결된 여행(목적지·기간) 배지 표시,
  연결된 여행이 없는 사고 접수는 국가만이라도 직접 입력 가능
- 추가질문·실수방지점검이 분류된 사고유형(L1)에 실제로 관련된 항목만 확인 — 휴대품 사고에 "의료비"·
  "다친 부위" 같은 무관한 항목이 뜨지 않도록 스코프
- 게스트로 접수한 사고는 회원가입 시점에 정리되어 계정 이력에 섞이지 않음
- 목록형 화면(청구결과·서류체크·담보비교)은 스크롤 대신 페이지네이션으로 분리
- **기존보험 연결 + 중복·공백 진단** — 실손·상해·일상생활배상책임 등 이미 가진 보험을 등록하면
  이번 여행자보험과 겹치는 담보·비는 담보를 약관 원문 근거와 함께 안내(위 전용 절 참고).
  판정 규칙은 코드가 아니라 `overlap_rule` 테이블에 근거 조항과 함께 시드되며, 근거를 못 찾으면
  시드 자체가 실패하므로 근거 없는 판정이 구조적으로 불가능
- **기존보험 수집 Provider 추상화** — 수동입력/목데이터/CODEF를 같은 인터페이스로 묶어
  환경변수만으로 전환. CODEF는 주민등록번호 처리 제약(개인정보보호법 제24조의2)으로 미연동 상태
- **실손 세대 자동 판정** — 가입 년월만 받아 1~4세대를 정함(2009년 표준화 이후 보험사별 보장내용
  동일). 가입시기를 모르면 추측하지 않고 비워 둠
- 탈퇴·게스트승격 시 기존보험 데이터도 함께 삭제 — SQLite가 FK를 강제하지 않아 고아 행이 남으면
  `user_id` 재사용 시 다른 사용자에게 노출될 수 있으므로 명시적으로 지움(회귀 테스트 포함)
- pytest 도입 — 진단 인용문이 실제 조항 원문의 부분 문자열인지, 안내 문구의 핵심 주장이
  인용문 안에 실제로 들어 있는지까지 자동 검증
- 모바일·태블릿·데스크톱 반응형 레이아웃 — 화면 크기별 아이콘/글자 크기 최적화
- Render 무료 호스팅 배포 — GitHub 연동 자동배포(`render.yaml` 블루프린트)

- **나이·성별별 실제 보험료 비교** — 각 사 다이렉트 사이트에서 직접 조회한 7개사 보험료를
  보험사 순위 화면에서 바로 비교(만 0~80세 × 남/녀, 2,794행). 산출 전제·출처·수집일을 항상 함께
  표시하고, 해당 나이가 가입연령 밖이라 값이 없는 보험사는 조용히 빼지 않고 사유를 밝힘

- **여행지 위험도 — 외교부 여행경보를 약관 전쟁·내란 면책과 연결** — 지금까지 위험도는 활동과
  여행일수만 봤습니다. 시리아에 가든 일본에 가든 "관광"이면 똑같이 낮음이 나왔습니다. 외교부
  여행경보(공공데이터포털, 208건/145개국)를 받아, 경보가 높은 곳이면 **그 보험사 약관의 전쟁·내란
  면책 조항 원문**을 함께 보여줍니다. 사고유형 `SPC_WAR_TERROR`에 매핑된 면책 조항을 그대로
  꺼내 쓰므로 새 판단 로직이 필요 없습니다. 다만 지금 면책으로 매핑된 곳은 카카오페이손해보험
  한 곳뿐입니다 — 나머지 보험사는 같은 유형에 전쟁위험 특별약관의 *보상하는 손해* 조항만
  매핑돼 있어 인용할 면책 원문이 없고, 그런 보험사에는 아무 문구도 붙이지 않습니다. 매핑이
  늘면 코드 변경 없이 그대로 채워집니다.

  경보는 국가가 아니라 **지역** 단위입니다. 일본의 3단계는 후쿠시마 원전 반경 30km, 필리핀의
  4단계는 민다나오 일부입니다(3·4단계 72개국 중 52개국이 일부 지역 경보). 그래서 "그 나라 일반
  지역의 단계"와 "지역별 경보"를 나눠 다룹니다 — 전국이 위험한 31개국은 자동으로 면책 조항을
  붙이고, 일부 지역만 위험한 나라는 **어느 지역인지 밝히고 "여행 경로에 포함되나요?"를 물은 뒤**
  체크했을 때만 붙입니다. 도쿄 여행자에게 출국권고를 띄우지 않기 위함입니다.

  경계: 경보 단계 자체를 보상 판정 근거로 쓰지 않습니다(외교부 자료와 약관은 출처가 다릅니다).
  "보상되지 않습니다"가 아니라 "이 약관에 전쟁·내란 면책 조항이 있으니 원문을 확인하고 보험사에
  직접 물어보라"까지만 하며, 이 문구는 테스트로 고정돼 있습니다. 보험사 순위 점수에도 넣지
  않습니다(약관 근거가 아닌 외부 자료라 보험료와 같은 취급).

- **표준약관 대조 — 보험사 약관을 금융감독원 법정 표준약관과 조문 단위로 대조(제3조 6개사·제4조 5개사)** — 지금까지
  비교는 전부 보험사 간 대조였습니다. 조항 문장을 규제 기준선(보험업감독업무시행세칙
  [별표15] 표준약관)과 대조하는 서비스는 시중에 없습니다. 금감원 자체 게시물에서 원문(HWP)을
  받아(2차 유통사 아님, 재배포 문제없어 저장소에 커밋), 해외여행 실손의료보험 표준약관
  제1~9조(제4조의2·제5조의2 포함 11개 조문)를 적재하고 보험사 상세화면에 "표준약관과 비교" 탭으로
  보여줍니다. 판정은 `overlap_rule`과 같은 원칙 — 코드가 아니라 `clause_standard_map`
  행 데이터로 두고, 표준·보험사 양쪽 원문에 실제로 있는 문구(anchor_phrase)를 못 찾으면
  시드가 예외를 던지고 롤백합니다. 현재 표준 11개 조문 × 7개사 중 근거를 확보한 11칸만
  채워져 있고(제3조 6개사, 제4조 5개사), 나머지는 근거 없이 "표준과 같다"고 단정하지 않고
  비워 둡니다(`docs/compliance/source_register.md` 매핑 커버리지 참고).

  참고: 이 표준약관은 **해외여행 실손의료보험** 전용이라, 기존보험 연결 기능의 "확인불가"
  3건(사용자가 이미 가진 **일반(국내) 실손의료보험**의 보장범위 관련)과는 별개 문서다 —
  일반 실손의료보험 표준약관을 확보하면 그 갭은 별도로 좁힐 수 있다.

- **항공지연 통계 — 약관의 지연기준시간을 실제 숫자로 체감** — 약관은 "4시간 이상
  지연"처럼 기준시간만 적혀 있어, 그게 자주 걸리는 기준인지 감이 안 옵니다. 한국공항공사가
  공공데이터포털에 공개한 실제 출도착 지연 통계(2017~2025.5, 인천공항을 제외한 전국공항이
  집계 범위, 지연 45만 7,877건)를 받아, 보험형광펜·청구전점검 화면의 지연기준시간 배지
  옆에 "국제선 실제 평균 지연시간은 약 61분 — 이 기준(240분)은 평균의 약 4배"처럼 크기
  비교를 붙입니다. 원본에 총 운항편수가 없어 **"지연 발생 확률"은 계산하지 않습니다**
  — 확률을 주장하면 근거 없는 숫자가 되므로, 크기 비교(평균 대비 몇 배)까지만 씁니다.
  새 화면을 만들지 않고 기존 "보험 형광펜"·"청구 전 점검" 흐름에 이미 있는 조항 카드에
  그대로 얹었습니다.

- **부지급 사유 조항 확인 — "보험 형광펜"에서** — 지금까지 생애주기는 "여행 전 →
  사고 후 청구 준비"에서 끝났습니다. 거절당한 다음이 비어 있었습니다. 보험사가 부지급
  통지서에 인용한 조항 번호나 문구를 입력하면, 그 보험사 약관 원문에서 실제 조항을 찾아
  보여주고 그 조항이 어떤 사고유형에 직접/조건부/면책 중 무엇으로 매핑돼 있는지까지
  같이 보여줍니다(`GET /clauses/search`, 기존 `clause_incident_map`을 그대로 재사용).
  **법률 자문이 아닙니다** — 조항 원문과 매핑 사실까지만 보여주고, 이번 사고에 실제
  적용되는지는 사람이 판단해야 한다는 것을 화면에 명시하며, 확실하지 않으면 보험사에
  직접 묻거나 금융감독원 분쟁조정(1332)을 안내합니다. 새 화면 대신 "보험 형광펜"에서
  사고를 아직 안 골랐을 때(원래는 막다른 빈 화면이었던 자리)에 얹었습니다 — 부지급
  통지서는 앱에 접수한 사고와 무관하게 받을 수 있어 사고 선택을 강제하지 않습니다.

- **보험금 부지급률 공시 — "보험료 비교공시" 화면에 함께** — 손해보험협회 공시실에서
  손해보험사의 보험금 부지급률·청구이후 해지비율(2025년 하반기, 업계평균 포함)을 받아,
  보험료 비교 화면에서 고른 보험사 옆에 나란히 보여줍니다. **전체 보험종목 기준
  공시**라 여행자보험만의 수치가 아니라는 점을 화면에 그대로 밝히고("이 보험사가
  전반적으로 보험금을 얼마나 안 주는 편인가"의 참고 지표로만 사용), 약관 근거가 아닌
  외부 공시 자료라 보험사 순위 점수에는 넣지 않습니다(보험료와 같은 취급). 새 화면
  없이 기존 "보험료 비교공시" 페이지에 얹었습니다.

- **「현지에서」 — 해외 현지에서 쓰는 서류 요청 카드** — 생애주기가 "여행 전 → 사고 접수
  → 청구 준비 → 부지급 후"로 이어지는데, 정작 청구 결과가 결정되는 **현지에서의 몇
  시간**이 비어 있었습니다. 해외에서 부지급이 나는 흔한 이유는 담보가 없어서가 아니라,
  약관이 요구하는 형식(예: 삼성 제7조 ②항 *"…국외의 의료관련법에서 정한 의료기관에서
  발급한 것이어야 합니다"*)을 모른 채 영수증만 받아오기 때문입니다. 귀국하면 그 서류는
  영영 못 받습니다.

  세 가지를 한 화면에 둡니다. ① 귀국하면 못 받는 서류(`required_doc_std.acquire_location`
  = `현지only`, 14종 중 8종)를 맨 위로 올리고 여행 종료일 기준 D-day를 함께 보여줍니다.
  연결된 사고가 있으면 그 사고의 `evidence` 상태로 진행률을 내고, 없으면 0/N으로 지어내지
  않고 목록만 보여줍니다. ② 사고유형을 고르면 그 유형의 필요서류를 **현지어와 한국어를
  병기해서** 창구에 그대로 보여줄 수 있는 카드로 만듭니다. ③ 서비스워커(PWA)가 이 응답을
  캐시해 로밍이 없거나 백엔드가 잠들어 있어도(Render 무료 플랜 cold start) 열립니다.

  경계: **조항 원문은 번역하지 않습니다.** 근거 그 자체이므로 한국어 원문 그대로
  인용하고, 번역 대상은 서류명·요건 표시문구·안내문 셋뿐입니다(`OnsitePhraseI18n`이
  종류 자체를 강제합니다). 검수한 번역 8개 언어를 시드해 두고, 그 외 국가는 Gemini로
  만들어 같은 테이블에 캐시하며, Gemini가 없으면 기능을 막지 않고 **한국어만** 보여줍니다
  — 서류 목록·약관 요건·근거 조항은 번역 없이도 그대로 유효하기 때문입니다(서류 사진
  확인처럼 LLM 없이는 결과 자체가 존재할 수 없는 기능과 다르게 다룹니다). 오프라인은
  열람까지만이고, 오프라인 중 쓰기·동기화는 범위 밖입니다.

  ```
  GET /trips/{trip_id}/onsite     이 여행 기준(등록한 보험사 요건으로 좁힘)
  GET /onsite?country={국가}       여행 없이 나라만으로(게스트 가능)
  ```

- **사고 시뮬레이션 — "이 여행에서 이런 일이 나면 보험사별로 어떻게 갈리는가"** — 지금까지
  보험사 비교는 전부 표의 숫자(보험료·지급한도)였습니다. 사용자는 숫자 차이를 체감하지
  못합니다. 여행 정보(활동·렌터카·여행경보)로 시나리오를 자동으로 고른 뒤 **기존 청구
  판정 엔진에 그대로 태워서**, 같은 사고에 7개사 결론이 조항 원문과 함께 갈리는 것을
  보여줍니다. 예를 들어 활동에 "스쿠버다이빙"을 적으면 기존 *활동 기반 면책 우선* 판정
  (`claim_review.rank_maps`)이 그대로 발동해 7개사 중 5개사가 면책으로 뒤집히고, 그 근거가
  된 문구가 실제로 담긴 조항 구간이 인용됩니다. 나머지 DB손해보험·카카오페이손해보험은
  "스쿠버다이빙"이 적힌 면책 조항이 매핑돼 있지 않아 직접으로 남습니다 — 없는 근거를
  만들어 붙이지 않기 때문입니다. 배상책임 시나리오에서는 카카오페이손해보험만
  **확인불가**로 남습니다(아래 한계에 적힌 담보 제거 이력이 그대로 드러납니다).

  새로 만든 것은 조회 범위뿐입니다 — `relevant_coverages_for_type`이 사용자가 등록한
  담보 기준이라 가입 전에는 빈 결과가 나오므로, `policy_version` 전체 담보를 도는 자매
  함수를 두되 **판정 로직은 손대지 않고 그대로 호출합니다.** 두 화면의 판정 기준이
  갈라지면 어느 쪽이 맞는지 설명할 수 없게 됩니다. 시나리오는 코드 분기가 아니라
  `simulation_scenario` 행에 있고(`overlap_rule`과 같은 원칙), **L1 대분류로만** 걸립니다
  — 여기엔 자유서술이 없어 L2를 추론할 근거가 없으므로 세분화는 사용자가 직접 고릅니다.
  근거 조항이 없는 보험사는 조용히 빼지 않고 확인불가로 남깁니다(빠지면 "그 보험사가 더
  나은가?"로 오독됩니다). 여행경보 시나리오는 **전국 단위 경보 국가에서만** 뜹니다 —
  국가 최고 단계로 판정하면 도쿄 여행자에게 소요 시나리오가 붙습니다.

  ```
  GET /trips/{trip_id}/simulation                       L1 기준
  GET /trips/{trip_id}/simulation?select={코드}:{L2id}   세분화 선택(다른 L1의 L2면 400)
  ```

미구현/알려진 한계:
- 담보별 가입금액(상품요약서 기준 숫자)은 아직 반영되지 않음 — 약관에 명시된 조건·한도까지만 반영됨.
  상품 전체 보험료는 위 비교공시 수집으로 반영됨
- 카카오페이손해보험은 검수 중 원문이 아닌 요약본으로 확인된 6개 담보를 한 번 걷어냈다가,
  이후 이전 판 약관(2025년 판)에서 조항 원문을 확보한 만큼만 되돌려 놨습니다. 지금 상태는
  **휴대품손해·구조송환** 담보에 2025년 판 조항이 각각 2건·3건 붙어 있고, **여행중단·여권분실·
  항공기납치**는 담보 행만 있고 조항이 0건이며(그래서 이 담보로는 근거를 인용하지 못하고
  확인불가로 남습니다), **배상책임**은 담보 자체가 아직 없습니다 — 이 넷은 재추출이 필요합니다
- L1 분류가 애매할 때 후보 2~3개를 직접 골라 확인하는 UX는 아직 없음(추가 질문으로만 좁힘)
- 벡터 임베딩 기반 RAG는 구현되어 있지 않음(SQL 기반 후보 필터링만 사용)
- 평가는 두 겹입니다(`docs/evaluation.md`). ① 사고유형 분류 자체를 160건 골드셋으로 L1/L2
  Accuracy·Macro-F1·confusion matrix와 abstention까지 재고, ② 그 위에 **청구지원 E2E 골든셋
  40건**(easy 24·hard 8·ambiguous 8)으로 "자유서술 → L1/L2 → 가입담보 → 약관 → 필수서류 →
  직접/조건부/면책" 연결 전체를 잽니다. E2E 쪽은 정답을 적어두지 않고 실행 시점에
  `ClauseIncidentMap`·`CoverageDocMap`을 조회해 현재 KB와 대조하므로, 모델 출력에 맞춰 정답을
  고쳐 점수를 부풀릴 수 없습니다. 근거 없는 담보를 권하지 않았는지(unsupported recommendation
  rate)와 인용이 원문에 실재하는지(citation grounding rate)를 함께 재는 것이 이 평가의 목적입니다
- 실제 PASS/FDS 등 금융권 수준 본인인증·이상거래탐지는 외부 유료 연동이 필요해 이번 프로젝트
  범위에서 제외
